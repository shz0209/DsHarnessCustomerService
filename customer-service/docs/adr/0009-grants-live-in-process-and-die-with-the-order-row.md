# 校验凭证活在进程内，以订单快照判定「订单已变更」

[ADR-0002](0002-validation-enforced-by-single-use-grant.md) 定了凭证的语义（一次性、十分钟、订单一经变更即失效），但没说这三条落在哪里。这里的决定是：凭证**只活在签发它的那个进程的内存里**，不落库；「订单已变更」的判定方式是**签发时记下整行 Order，使用时重新读出来逐字比对**，任何一处不同即视为变更。

## 为什么活在进程内

凭证的全部寿命是十分钟，且校验本身没有副作用、随时可以重跑——进程重启丢掉的只是一次重新校验，与登录态绑定（会话与客户的绑定同样只在内存里，见 [ADR-0004](0004-customer-identity-from-login-not-parameter.md)）是同一种取舍。落库要为此多一张表、一条过期清理路径，而这条路径服务的是一个十分钟后就无意义的对象。

## 为什么比对整行，而不是状态位或版本号

- **只看状态位**（规则真正读的那个字段）会让「客户确认时是这笔钱、这个地点」这件事失去保护：订单金额或租借地点被改过之后，凭证仍然有效，而客户当时确认的是改之前的那一笔。
- **在 Order 上加版本号或 `updatedAt`** 要求每个写入方都记得维护它，漏一处就是一个静默存活的陈旧凭证；而比对整行不需要任何人配合——动作工具为了执行本来就要把这一行读出来。多出来的字段（例如退款 ticket 要加的 `refundedAt`）也自动进入比对，不需要回来改这张表。

比对按 key 排序后序列化，所以「同一批值换了个 key 顺序重写」不算变更，只有值的差异才算。

## 后果：规则只在签发那一刻判定

动作工具**不重新跑一遍校验规则**。于是存在一个不超过凭证寿命（十分钟）的窗口：1 小时 59 分时校验通过、2 小时 04 分才执行，这笔订单会被结掉，尽管执行时它已经不满足两小时的窗口。

这是有意的，不是漏洞：判定只发生在一个地方（[ADR-0002](0002-validation-enforced-by-single-use-grant.md) 的「强制发生在唯一能做决定的那次操作里」），否则「凭证过期」就成了第二套时间规则，两处判定迟早会出现不一致的口径——而客户听到的结论来自校验那一次。凭证的十分钟寿命正是这条结论的保鲜期，也是「隔太久才执行就要重新校验」这条要求的落点。订单**状态**上的变化由上面那行快照负责，与时间无关；时间流逝本身不改变订单，只让结论变旧。

窗口内这次校验之后**再校验一次、结论变成不允许**时，动作就做不成了：不允许的那次校验会作废此前签发的凭证（`revoke`），所以手上那张永远等于最近一次的结论。若不这样，客服可能刚说完「不行」就把单子结掉——规则一致性的演示最不能出现这一幕。作废不需要额外代价：校验没有副作用，条件再满足时重跑一次即可。

## Considered Options

- **凭证落库。** 好处是重启后仍可用、多进程部署也能工作。放弃它是因为这套演示是单进程的，而落库会把「凭证属于哪个会话」这条绑定拆到两个生命周期里去管（会话绑定本来就不落库）。
- **把校验结论写进会话日志，动作工具回头去读日志。** 看起来更"可回放"，但日志是给人看的历史，不是权限来源：它无法表达"已用掉"，也挡不住同一回合内重复执行。凭证是一次性的**状态**，不是一条记录。
- **把动作工具与校验合并成一个工具**（校验通过就顺手执行）。结构上确实无法绕过，但业务上校验与执行是两步，合并会让返回值同时承担"判定"和"执行结果"两种含义，也让"校验通过后隔一会儿才执行"这种真实节奏无法表达——[ADR-0002](0002-validation-enforced-by-single-use-grant.md) 已否掉这条路。
