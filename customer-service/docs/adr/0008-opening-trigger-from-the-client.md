# 开场：客户端请求，宿主投递一条自有来源的消息

客户登录后客服要主动开口，而模型只在收到回合输入时才运行——[ADR-0001](0001-order-card-as-blocking-tool.md) 早已写明这个代价：「开场那张卡片必须由模型发起（需先触发一个回合）」。因此浏览器半边一接管到登录会话，就向 `POST /customer-service/opening` 发一次请求，宿主插件据此构造一条 user 角色的消息、来源写成自己的 `source.kind`（`customer-service`），经 `resolveAgent` + `agent.followup` 投递——harness 的定时提醒与 Webhook 走的正是这条路径。同一个插件再用一段系统提示词告诉模型这条消息是什么意思，并规定开场动作。

**不用 `sessionController.prompt` 投递**，尽管它最省事：那条路径把来源固定写成 `user`，于是对话区把开场显示成客户自己发的一条气泡——「你好」。客户没有说过这句话，客服的开场不该由客户的嘴说出来。自带来源的消息则落在 harness 为「不是人说的话、但启动了这一轮」准备的呈现上：折叠的触发行。

代价有两条，都记在这里：

- **这条消息带不了浏览器时区。** harness 只从浏览器自己发出的消息里读时区（`packages/context/time-context/src/request-zone.ts`），于是开场这一轮的时钟上下文会说「浏览器时区不可用，请让客户澄清」；而时钟注入每十分钟才有一次，接下来几分钟的回合会一直沿用这句话。所以宿主把登录时拿到的时区记在会话账本上，由开场协议直接说出「客户浏览器的时区是 X」，并明说注入的时钟若说不可用就按它读、不要反问客户。
- **消息由本目录手工构造。** harness 的构造函数 `createUserMessage` 在仓库外 import 不到（[ADR-0006](0006-out-of-tree-plugin-authoring-constraints.md)），所以 `role`、`id`、`content`、`source` 四个字段与「深冻结」这条约定由 `openingMessage()` 照着写。升级 harness 时要人工核对的约定因此多一处。

## Considered Options

- **`sessionController.prompt` 投递（最初的做法）。** 一条调用就完成投递与校验，消息还自带浏览器时区；代价是 `source.kind` 固定为 `user`，客户在对话里看到自己没打过的「你好」。
- **浏览器半边直接调用 harness 的客户端会话接口投递。** 界面呈现与上一条完全相同（同样是 `user` 来源的气泡），却还要客户端先 retain 会话、等它 ready；且开场文案会住在浏览器半边、对它的解释住在宿主半边。
- **完全不显示任何一行。** harness 没有这种机制：模型要开口就必须有一个回合输入，而这个输入要么是客户侧的气泡，要么是非人类输入的触发行。要做到「一行都不出现」得改 `packages/` 里的对话渲染，超出本目录不改外部的边界（[ADR-0003](0003-out-of-tree-local-plugin-directory.md)）。
- **客户端直接把卡片渲染出来，不经过模型。** 违反 [ADR-0001](0001-order-card-as-blocking-tool.md)：卡片的作答就不再是工具返回值，被确认的订单也不再天然进入上下文。

## 后果

- 开场只发生在**已登录**的会话上：`/opening` 要求登录 cookie，并只认发起它的那个会话；未登录时返回 401，请求体里带了非字符串的 `clientTimeZone` 时返回 400。
- 「已开场」与那条时区记在本进程内，与登录绑定同生共死：重启后绑定没了、需要重新登录，因此不会留下过期条目。
- 触发消息不是客户说的话，客户在对话区看到的是一条可展开的系统触发行；它仍是一条落盘的会话事件，整轮开场照样可以从会话日志重建。
