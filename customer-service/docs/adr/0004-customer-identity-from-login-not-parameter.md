# 客户身份由登录态决定，不作为工具参数

工具**不接收**客户 id。宿主侧在登录成功时把 harness 会话与客户绑定，工具执行时从当前 agent 的会话查出客户，只在该客户的订单范围内查询与操作；查不到绑定（未登录）时工具失败并给出明确错误，而不是退化成一次全库查询。

## Considered Options

- **每个工具接收一个客户 id 参数，由模型填写。** 好处是工具签名自带上下文，可以脱离登录态独立调用与测试。放弃它是因为：参数一旦由模型提供，服务端就必须再校验它等于当前登录客户，否则模型可以查到、甚至改动别人的订单；那等于把同一条规则在签名里写一遍、又在执行处重写一遍。身份只保留一个来源更省事，也更难出错。
- **信任模型传入的客户 id。** 实现最简单，但把"模型可能填错或填别人"变成真实的数据事故，对这一套以"规则必然被执行"为卖点的演示不可接受。

代价是工具无法脱离会话单独调用，测试必须构造一个已绑定的会话。
