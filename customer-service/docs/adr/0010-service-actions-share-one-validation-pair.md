# 两个服务动作共用一份「校验 + 动作」实现，凭证只认签发它的动作

[ADR-0002](0002-validation-enforced-by-single-use-grant.md) 定了「先校验、拿凭证、再执行」这条协议，[ADR-0009](0009-grants-live-in-process-and-die-with-the-order-row.md) 定了凭证活在哪里。退款（issue #8）是第二个用这套机制的动作，于是有三个问题要当场答：协议写几份、凭证怎么区分动作、退款规则要不要判「已退款」。

## 协议只写一份

`plugins/tools/validation.js` 的 `validationPair` 是唯一实现。`manual-return.js` 与 `refund.js` 各自只声明自己那一半：两个工具名、这个动作的说法、固定规则、写入、办完那句话，以及两个工具各自的开场白；工具描述里关于凭证的几句（怎么签发、怎么用、没有凭证会怎样）由这里拼上，不随动作复制——那是协议的话，不是某个动作的话。

理由：这套协议本身就是不变量——哪里签发、哪里取走、没有凭证时做什么，都是「唯一能做决定的那次操作」。两份拷贝就是两次走样的机会，而走样的方式很安静：一个动作仍然拒绝，另一个悄悄放行。

## 凭证按动作分账

凭证绑定的「动作」就是执行它的工具名（`manual_return` / `refund`）。于是人工还宝的凭证退不了款，退款的凭证也结不了单，不需要第二个动作枚举，也不可能出现两个动作共用一个名字。

## 退款规则先状态、后等级，且不判「已退款」

`validate_refund` 只看两件事，而且**先看订单状态、再看会员等级**：仍是「进行中」就直接拒绝，说的是「不允许退款，该订单仍在进行中」；只有订单已「已归还」时才看等级，铂金或黑金允许，其余等级得到「非铂金/黑金会员，不允许退款」。顺序与人工还宝「状态先于时间」同理：状态决定的事用状态的话说——对一笔「进行中」的订单说客户等级不够，对铂金客户就是假话。

已经退过款的订单仍是「已归还」，等级也仍然够，所以再问一次结论还是「允许退款」，`refund` 只是把退款时间改写一次。要单独判「已退款」，同样得新增一条规则和一句文案——和「进行中」那一句一样，这是产品决定（issue #8 已按此更新），不是实现时能顺手加的。代价也确实低：退款只是一个标记，重复标记不改变任何东西（这套演示里没有真实资金）。

## Considered Options

- **校验与动作合成一个工具。** [ADR-0002](0002-validation-enforced-by-single-use-grant.md) 已否掉：判定与执行是两步，合并会让返回值同时承担两种含义。
- **每个动作各写一份实现。** 单看一个动作更直白，但把不变量复制成两份，凭证相关的工具描述也要跟着复制——正是这一条让 `validation.js` 存在。
- **在凭证里加动作枚举，而不是用工具名。** 多一个必须与工具名保持一致的取值，换不来任何东西：两个动作的工具名本来就不同名。
