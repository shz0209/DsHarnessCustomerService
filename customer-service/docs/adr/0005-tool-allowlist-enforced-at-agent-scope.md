# 工具白名单在 agent 作用域强制

客服 agent 只能看到并调用那 5 个业务工具，其余一律不可用。实现方式是在 agent 作用域上施加工具白名单（`tools.restrict({ allow })`，必要时叠加一个 guard 作为第二道防线），而不是靠"不加载其它的工具插件"。

## Considered Options

- **只不加载其它工具行。** 表面上最省事，但做不到完整：有些工具注册在宿主层，不对应任何可禁用的加载行（例如 `working_directory`），白名单之外总会有漏网的。而且它对"以后新增的工具行"没有免疫力——新装一个 bundle，工具就重新开放了。
- **在系统提示词组装阶段增删工具。** 仓库自己的文档明确劝阻这种做法，因为那条路径绕开了工具列表与调用派发共用的解析器，会让"藏起来"和"调不动"脱钩。

选择作用域白名单的理由：工具列表、按名字查找、调用派发三者共用同一个解析器，所以白名单是**真正强制**的，而不是伪装。代价有两点——限制必须从一个比工具更深的作用域施加（agent 作用域），且白名单里的名字必须已经在祖先作用域注册完毕，否则启动即报错；这个报错是我们要的：配置错了就响亮地失败，绝不静默放开。

另有一处保留名：PTC 模式下的 `run_code` 是传输层而非能力，无法被白名单排除。因此白名单在同一个作用域上还要声明 native 呈现（`tools.presentAs('native')`），与限制一起施加、一起撤销。

这里不用「把 profile 的 `mode` 配置成 native」：那是配置，不是不变量，换个 profile 或改一行 `cordis.yml` 就能把 `run_code` 放回来。改成按作用域声明之后，任何配置都放宽不了客服 agent 够得着的工具集合——链上就近的作用域说了算，所以即使某个 agent preset 给祖先作用域声明了 PTC，agent 自己这一层的 native 仍然覆盖它。

只有**同一个**作用域被声明两次才算组合冲突：`presentAs` 只在被调用的那个作用域上查重（`packages/core/scope/src/store.ts` 的 per-scope layer），命中即抛错。这正是想要的：同一层出现两种呈现说明组成写错了，响亮地失败，绝不静默放开。

## 后果：作用域过滤器盖不住自己这一层

`restrict` 只过滤继承来的名字（全局层与祖先作用域），**自己这一层的注册不过滤**——注册表有意如此，因为代理运行时往子 agent 自己那层塞的回报工具不该被它自己的白名单削掉。而 web profile 的 agent preset 恰好把 `subagent` 这类工具注册进 agent 自己那层，于是它绕过了 `restrict`：实测把 `--patch` 覆盖层跑起来后，模型看到的工具列表是 `search_orders` 与 `subagent` 两项。

补上这个缺口要三件事，各管一头：

- `tools.guard(...)` 管**能不能调**。它只否决「当前视图仍然解析得到、却不在白名单里」的名字；视图里根本没有的名字一律放行，让注册表照旧抛出它自己的 `ToolNotFoundError`（带 `UNKNOWN_TOOL` 代码）。否决时用的也是注册表那句话——`unknown tool "<名字>"`：作用域机制本来就要求「看不见的执行与不存在的工具无从分辨」，白名单这边不能反过来把注册表的形状漏给模型。
- `system-prompt/assemble` 的监听器（`prepend`，最后收口）管**看不看得到**。模型的工具列表来自组装后的提示词，不是注册表视图，所以要在这里按同一个白名单过滤一次。这正是上面「考虑过的选项」里被否掉的那条路径——单独用它会让隐藏与派发脱钩，所以这里只把它当作 `restrict` 的补集，并且与 guard 共用同一个 `ALLOWED_TOOLS` 常量。
- 同一个监听器还要丢掉被隐藏工具的**提示词段落**：每个工具的引导段落都叫 `tool:<工具名>`，于是用同一把钥匙过滤即可。只藏工具不藏段落的话，实测出来的提示词里仍有一句「Start independent delegations with `subagent`」在指使模型去调一个它没有的工具。

四条声明（restrict、presentAs、guard、组装过滤）在同一个作用域上一起施加、一起撤销，白名单才是完整的不变量；少任何一条都有一个能实测出来的缺口。
